# Test Quality

A green test suite is a claim, not a fact. This skill is about the gap between
the two — the three ways a suite passes while verifying nothing, and what to do
instead.

The most expensive version of that gap in research code: a suite that passes on
every commit and still lets a wrong number reach a manuscript, because every
assertion in it was computed the same way the code computes it.

## The three failures

### 1. Tautological assertions (the dominant one)

The expected value is recomputed the way the code computes it, so the test passes
by construction and can **never disagree with the code**.

```python
# BAD — the assertion restates the implementation
def test_mean_concentration():
    rows = load_rows("run01.csv")
    expected = sum(r.conc for r in rows) / len(rows)   # same formula as the code
    assert mean_concentration(rows) == expected
```

If `mean_concentration` should have excluded the blank well, this test passes
anyway. It will pass forever, through every refactor and every bug.

```python
# GOOD — the expected value comes from an independent source
def test_mean_concentration():
    # 3 wells at 2.0, 4.0, 6.0 mM; blank excluded -> 4.0 (hand-worked)
    assert mean_concentration(load_rows("fixtures/three_wells.csv")) == 4.0
```

**The rule: an expected value must come from outside the implementation.** Valid
sources are a hand-worked example, a value read off the instrument, a number
published in a paper or standard, a result from an independent tool, or a literal
someone reasoned about once and wrote down. Not a re-derivation, and not a
snapshot generated by the same code on a day it happened to look right.

This applies with force to anything numeric. A snapshot test over a computed
array records what the code did, not what it should do — useful for catching
*unintended change*, worthless for catching *wrong from the start*. If you use
one, say which of the two it is doing.

**Floating point.** Comparing floats with `==` makes a test that fails on an
unrelated platform. Assert with a tolerance, and pick the tolerance from the
measurement's own precision, not from whatever makes the test pass today.

### 2. Coupling to internals

The test reaches past the interface — mocking internal collaborators, calling
private functions, or verifying through a side channel instead of the interface.

```python
# BAD — verifies through a side channel, and mocks an internal
def test_save_result_writes_row(tmp_path):
    with mock.patch("pipeline.normalise") as m:
        save_result(record, tmp_path)
    assert m.call_count == 1
    assert (tmp_path / "internal" / "cache.bin").exists()
```

```python
# GOOD — verifies through the interface the caller uses
def test_saved_result_can_be_read_back(tmp_path):
    save_result(record, tmp_path)
    assert load_result(tmp_path, record.id).concentration == record.concentration
```

**The tell:** the test breaks when you refactor, while the behaviour has not
changed. Every such test is a tax on every future change, paid in false alarms
until someone deletes it or stops trusting the suite.

Test names carry the same signal. `test_calls_normalise_once` names *how*;
`test_blank_well_is_excluded_from_mean` names *what*. If you cannot name the
behaviour, you may be testing structure.

### 3. Writing all the tests first

Writing a full suite before any implementation verifies **imagined** behaviour.
You test the shape of what you expect, commit to that structure before you
understand the problem, and end up with tests insensitive to the changes that
matter.

Work in **vertical slices** instead: one test → the smallest implementation that
passes it → repeat. Each test responds to what the previous one taught you.

## Where tests go: seams

A **seam** is the public boundary where you can observe behaviour without
reaching inside. Tests live at seams.

**Agree the seams before writing tests.** You cannot test everything; naming the
seams up front is how the effort lands on the critical paths — the parsing step
that silently drops rows, the unit conversion, the filter that decides which
replicates count — instead of spreading evenly over trivia.

Prefer the **highest seam that still reaches the behaviour**. Fewer seams means
fewer tests to rewrite when the internals change. A test at a seam too shallow to
reach the real pattern (one input row for a bug that needs two rows to interact)
gives false confidence, which is worse than no test.

## What a good test looks like

- It reads like a specification: the name states a capability or a rule.
- It goes through the public interface only.
- It survives an internal refactor untouched.
- Its expected value is traceable to something outside the code.
- It makes one logical assertion.
- It is deterministic: seeded, fixed input file, no wall-clock or network.

## For research and data code specifically

- **Fixtures are data, and they belong under version control** next to the test,
  small enough to read. A test that depends on a file someone has locally is a
  test that will be deleted in six months.
- **Test the edges the data actually has**: the empty file, the single row, a
  missing column, a NaN in the middle, duplicated identifiers, a unit written
  two different ways. These are where analysis code fails in practice, and none
  of them appear in the happy-path fixture.
- **Pin the units in the assertion**, in the name or a comment. A test asserting
  `4.0` says nothing about mM versus g/L; a suite that is silent on units cannot
  catch a conversion bug.
- **A converged fit is not a passing test.** A test that only asserts the
  optimiser reported success asserts nothing about the answer. Assert on a
  recovered parameter against a known synthetic ground truth — generate data from
  known parameters, fit it, and check the fit gets them back within tolerance.
  See the `scientific-validation` skill for the plausibility axes that sit past
  what a unit test can reach.

## Review checklist

Run this over a suite before trusting it:

- [ ] Does any expected value get recomputed the way the code computes it?
- [ ] Would any test still pass if the function returned a plausible wrong answer?
- [ ] Does any test mock something internal to the module under test?
- [ ] Does any test assert on call counts, ordering, or private state?
- [ ] Does any test name describe *how* rather than *what*?
- [ ] Do the fixtures include anything other than the happy path?
- [ ] Are floats compared with a stated tolerance?
- [ ] Is every test deterministic (seed, fixed inputs, no network)?

The second question is the sharpest one. If you cannot construct a wrong return
value that the test would still accept, the test has real detection power. If you
can, the test is decoration.
