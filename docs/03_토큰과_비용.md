# 03. 토큰과 비용 — 왜 어떤 대화는 비싸고 어떤 대화는 싼가

이 문서는 Claude(그리고 대부분의 LLM 도구)를 쓸 때 반드시 알아야 할 개념인 **토큰(token)**을 설명합니다.
토큰을 이해하면 "왜 방금 그 질문이 오래 걸렸지?", "이번 달 사용량이 왜 이렇게 많지?" 같은 질문에 스스로 답할 수 있습니다.

---

## 1. 토큰이 뭔가요? — "글자 조각, 곧 돈"

AI 모델은 문장을 통째로 읽지 않습니다. 문장을 **토큰**이라는 작은 조각으로 잘라서 처리합니다.

- 토큰은 단어 하나일 수도, 단어의 일부일 수도, 공백이나 문장부호 하나일 수도 있습니다.
- 영어는 대략 "단어 하나 ≈ 토큰 1~1.3개" 정도지만, **한글은 글자 단위로 더 잘게 쪼개지는 경향**이 있어서 같은 의미를 담은 문장이라도 영어보다 토큰 수가 더 많이 나오는 경우가 흔합니다.
- 예시 감각 (정확한 개수는 모델마다 다르지만 감을 잡기 위한 예시):
  - `"안녕하세요"` → 대략 토큰 3~5개
  - `"Hello"` → 대략 토큰 1~2개

**왜 이게 "돈"과 같은가?**

AI 서비스는 보통 **입력 토큰 수 + 출력 토큰 수**를 기준으로 요금을 매깁니다. 즉:

- 내가 보낸 질문, 첨부한 코드, 대화 기록 전체 → **입력 토큰**
- AI가 대답한 내용 → **출력 토큰**

이 둘을 합친 만큼 비용이 발생합니다. 그래서 토큰 수 = 곧 돈이라고 이해하면 됩니다. 긴 문서를 통째로 붙여넣고 질문하면, 그 문서 전체가 매번 입력 토큰으로 계산된다는 점이 특히 중요합니다.

### 세션이 길어질수록 왜 더 비싸지나요?

대화형 AI는 이전 대화 내용을 "기억"하기 위해, 매 턴(turn)마다 **지금까지의 대화 전체를 다시 모델에 넣어줍니다.** 즉:

- 1번째 질문: 입력 = 질문 1개
- 2번째 질문: 입력 = 질문 1 + 답변 1 + 질문 2 (전체 누적)
- 10번째 질문: 입력 = 이전 대화 9턴 전체 + 질문 10

그래서 세션이 길어질수록 매 턴 입력 토큰이 눈덩이처럼 불어납니다. (이 문제를 완화하는 "캐싱"이라는 기술이 있지만, 그래도 대화가 계속 쌓이는 방향 자체는 바뀌지 않습니다.)

---

## 2. 내 사용량을 어떻게 보나요? — `/usage`

Claude Code(터미널에서 쓰는 Claude)는 `/usage`라는 명령어로 현재 사용량과 한도를 확인할 수 있습니다.

```
/usage
```

이걸 입력하면 대략 다음과 같은 정보를 볼 수 있습니다.

- 이번 주기(예: 5시간 단위, 또는 주간) 동안 얼마나 썼는지
- 남은 한도가 몇 %인지
- 언제 한도가 초기화되는지

**초심자를 위한 팁**

- 정확한 숫자는 항상 `/usage`로 직접 확인하세요. "느낌상 많이 썼다/적게 썼다"로 판단하지 말고, 실측값을 보는 습관을 들이는 게 중요합니다.
- 사용량이 갑자기 급증했다면, 보통 다음 중 하나가 원인입니다.
  1. 아주 긴 파일/문서를 통째로 붙여넣었다
  2. 세션(대화)을 하나로 너무 오래 끌고 갔다
  3. 간단한 일에 필요 이상으로 강력한(비싼) 모델을 계속 썼다

---

## 3. 아껴 쓰는 법 — 초심자를 위한 3가지 습관

### (1) 간단한 일은 저렴한 모델에게

모델에는 등급이 있습니다. 흔히 "가볍고 빠른 모델"과 "무겁고 똑똑한 모델"로 나뉘는데, 가격 차이가 꽤 큽니다.

- **간단한 작업** (오탈자 확인, 단순 요약, 파일 하나 읽고 답하기, 형식 변환) → 저렴하고 빠른 모델로 충분합니다.
- **어려운 작업** (복잡한 코드 리팩터링, 여러 파일을 넘나드는 설계 판단, 정교한 논리적 검증) → 더 똑똑하지만 비싼 모델이 필요합니다.

즉, **모든 질문에 제일 비싼 모델을 쓸 필요가 없습니다.** 작업의 난이도에 맞는 모델을 고르는 것만으로도 비용이 크게 달라집니다.

### (2) 긴 세션은 나눠 쓰기

한 대화창에서 하루 종일 이것저것 다 물어보면, 앞서 설명한 "누적 입력 토큰" 문제 때문에 뒤로 갈수록 매 턴이 비싸집니다.

- 주제가 바뀌는 지점, 혹은 하나의 작업 단계가 끝나는 지점에서 **새 세션으로 넘어가는 것**이 좋습니다.
- 예: "코드 버그 고치기"가 끝났으면, 다음으로 "문서 작성"을 할 때는 새 세션에서 시작하기.
- 대화 중간에 필요 없어진 이전 맥락(예: 이미 해결된 에러 로그, 더 이상 안 쓰는 파일 내용)이 계속 쌓여있다면, 세션을 정리하고 새로 시작하는 편이 더 저렴하고 빠릅니다.

### (3) 붙여넣기 전에 "이 내용이 다 필요한가?" 한 번 생각하기

- 파일 전체가 아니라 **관련된 부분만** 보여주기
- 로그 전체가 아니라 **에러가 난 부분만** 붙여넣기
- 이미 답이 나온 대화는 새로 시작하기

이 세 가지만 지켜도 불필요한 토큰(=돈) 낭비를 크게 줄일 수 있습니다.

## 4. (참고) 우리는 이 원리를 도구 자동화에 어떻게 쓰는가

아래는 이 프로젝트에서 토큰/비용 개념을 실제로 어떻게 자동화에 활용하는지, **공개 가능한 수준**에서 설명하는 부분입니다. 실제 사용량 숫자, 청구/정산 정보, 개인 서버 스크립트는 포함하지 않습니다.

### 4-1. 토큰 실측 원리 — "세션 로그를 직접 읽는다"

Claude Code 같은 도구는 대화 세션을 로컬에 로그 파일(JSONL 형식 — 한 줄에 메시지 하나씩 JSON으로 기록된 파일)로 저장합니다. 이 로그 안에는 각 턴마다 사용된 입력/출력 토큰 수가 함께 기록되어 있습니다.

즉, "이번 세션에서 토큰을 얼마나 썼나?"를 추정이 아니라 **로그 파일을 파싱해서 실제 숫자를 집계**하는 방식으로 확인할 수 있습니다. `/usage` 명령이 보여주는 것도 결국 이런 실측 데이터를 요약한 것입니다. 핵심은 "감으로 판단하지 않고, 기록된 사실을 읽는다"는 원칙입니다.

### 4-2. 모델 라우팅 개념 — "일의 난이도에 맞는 모델 배치"

작업을 맡기기 전에, 먼저 "이 일이 쉬운 일인가, 어려운 일인가"를 판단합니다.

- **쉬운 일** (단순 조회, 파일 하나 확인, 정형화된 반복 작업) → 저렴하고 빠른 모델에게 배정
- **어려운 일** (여러 파일에 걸친 설계 판단, 적대적 검증, 물리적/논리적 타당성 진단처럼 깊은 추론이 필요한 작업) → 더 강력한 모델에게 배정

이렇게 작업 난이도별로 모델을 다르게 배정하는 것을 **모델 라우팅**이라고 부릅니다. 사람으로 치면 "간단한 문의는 신입 직원에게, 복잡한 의사결정은 전문가에게" 배분하는 것과 같은 원리입니다. 이렇게 하면 전체 품질은 유지하면서 평균 비용은 낮출 수 있습니다.

### 4-3. 검증 게이트 개념 — "결과를 그대로 믿지 않고 한 번 더 확인한다"

AI가 내놓은 결과(코드, 계산, 글)를 작성한 것과 **동일한 주체가 스스로 검토하면, 자기 실수를 놓치기 쉽습니다.** 그래서 중요한 작업 결과물은 별도의 독립적인 확인 절차를 한 단계 거치도록 만듭니다. 이를 **검증 게이트(verification gate)**라고 부릅니다.

핵심 아이디어는 단순합니다.

1. 결과물을 만든다
2. (같은 맥락에 매몰되지 않은) 독립적인 시선으로 다시 확인한다
3. 문제가 없으면 통과, 있으면 되돌려서 고친다

이 절차는 특히 되돌리기 어렵거나(예: 실제로 전송되는 메일), 숫자가 정확해야 하거나(예: 계산 결과), 코드처럼 실수가 누적되면 나중에 찾기 힘든 작업에서 중요합니다. 비용을 아끼는 것도 중요하지만, **틀린 결과를 그대로 믿고 넘어가는 것이 장기적으로 더 큰 비용**이기 때문에, 무조건 다 저렴한 모델/한 번의 확인만으로 끝내지 않고 필요한 곳에는 검증 단계를 넣는다는 원칙입니다.

## 요약

| 개념 | 한 줄 설명 |
|---|---|
| 토큰 | AI가 글을 처리하는 최소 단위. 곧 비용의 기준 |
| `/usage` | 내 실제 사용량과 한도를 확인하는 명령어 |
| 모델 선택 | 쉬운 일=저렴한 모델, 어려운 일=강한 모델 |
| 세션 관리 | 대화가 길어질수록 비싸짐 → 주제 바뀌면 새 세션 |
| (심화) 토큰 실측 | 세션 로그(JSONL)를 파싱해서 실제 숫자를 집계 |
| (심화) 모델 라우팅 | 작업 난이도별로 자동으로 모델을 다르게 배정 |
| (심화) 검증 게이트 | 중요한 결과는 독립적으로 한 번 더 확인 |
