# AI에게 규칙 주기 — CLAUDE.md / AGENTS.md란?

이 문서는 "AI 코딩 에이전트한테 왜, 어떻게 규칙을 줘야 하는가"를 초심자 눈높이에서 설명합니다.
Claude Code, Codex, Cursor 등 요즘 AI 코딩 도구들은 대부분 같은 아이디어를 공유합니다:
**대화창에 매번 같은 말을 반복하지 말고, 파일 하나에 규칙을 적어두면 AI가 작업할 때마다 자동으로 읽는다.**

---

## 1. CLAUDE.md / AGENTS.md가 뭔가요?

- `CLAUDE.md`는 Claude Code가 세션을 시작할 때 자동으로 읽는 설정 파일입니다.
- `AGENTS.md`는 Codex를 비롯한 여러 AI 코딩 도구가 공통으로 채택하고 있는 동일한 역할의 파일입니다.
- 둘 다 **평범한 마크다운(.md) 텍스트 파일**입니다. 특별한 문법이나 프로그래밍 지식이 필요 없습니다.
- 위치는 보통 프로젝트 최상위 폴더(repo root)이며, 그 프로젝트에서 작업할 때마다 AI가 먼저 펼쳐보는 "안내문"이라고 생각하면 됩니다.

비유하자면: 새로 들어온 인턴에게 매번 구두로 "우리 회사는 이렇게 해요"를 반복 설명하는 대신, **업무 매뉴얼 한 장**을 책상에 붙여두는 것과 같습니다. AI는 이 매뉴얼을 매번 스스로 다시 읽고 그대로 따릅니다.

이 툴킷(sci-toolkit)에도 최상위 폴더에 `AGENTS.md` 파일이 준비되어 있습니다. 아직 내용이 비어 있다면, 이 문서에서 설명하는 방식대로 직접 채워 넣으면 됩니다. → `AGENTS.md` 참고

---

## 2. 왜 규칙을 줘야 하나요?

규칙 파일이 없으면 AI는 매 대화마다 "제로 상태"에서 시작합니다. 그러면:

- 어제 "이 폴더는 절대 건드리지 마"라고 말했어도 오늘 새 대화에서는 기억하지 못합니다.
- 같은 실수(예: 위험한 명령 실행, 잘못된 파일 삭제)를 반복할 수 있습니다.
- 매번 같은 맥락 설명을 반복해야 하니 비효율적입니다.

규칙 파일에 한 번 적어두면:

- **일관성**: 어떤 대화에서 시작하든 같은 기준으로 행동합니다.
- **안전성**: "이건 하면 안 됨"을 미리 박아두면 사고를 예방합니다.
- **효율**: 반복 설명이 사라지고, AI가 스스로 판단할 수 있는 기준선이 생깁니다.

즉, 규칙 파일은 AI를 "믿고 맡길 수 있는 범위"를 정하는 계약서에 가깝습니다.

---

## 3. 3단계 분류법 (3-Tier)

규칙을 쓸 때 아무렇게나 나열하면 나중에 관리가 안 됩니다. 다음 3단계로 나눠서 적으면 훨씬 명확해집니다.

| 단계 | 의미 | 예시 |
|---|---|---|
| ① 항상 지킬 것 | 매번 예외 없이 따라야 하는 기본 원칙 | "새 코드는 항상 테스트를 포함해서 작성한다" |
| ② 물어볼 것 | 애매하거나 되돌리기 어려운 경우, 진행 전에 먼저 확인 | "기존 파일을 완전히 덮어쓰기 전에는 먼저 물어본다" |
| ③ 절대 안 되는 것 | 어떤 상황에서도 금지 (하드 룰) | "`main` 브랜치에 직접 push하지 않는다" |

이렇게 나누는 이유는 간단합니다.

- ①은 "기본값"이라서 AI가 매번 알아서 하면 되는 것들입니다.
- ②는 "사람이 최종 결정권자여야 하는 것들"입니다 — 되돌릴 수 없거나, 외부로 나가거나, 비용/책임이 걸린 일.
- ③은 "논의의 여지가 없는 것들"입니다 — 보안 사고, 데이터 유실로 이어질 수 있는 행동.

## 4. 작은 예시 (범용, 개인정보 없음)

아래는 어떤 프로젝트에도 적용할 수 있는 **일반적인 예시**입니다. 실제로 쓸 때는 자신의 프로젝트 상황에 맞게 고쳐서 사용하세요.

```markdown
# AGENTS.md — 프로젝트 작업 규칙

## 항상 지킬 것
- 새로 작성하는 코드는 읽기 쉽게, 함수/파일 단위를 너무 길게 만들지 않는다.
- 기존 코드 스타일(들여쓰기, 네이밍 규칙)을 따른다.
- 변경 사항은 관련 테스트를 함께 업데이트한다.

## 물어볼 것
- 기존 파일을 대량으로 삭제하거나 구조를 크게 바꾸기 전에는 먼저 확인한다.
- 외부 서비스로 데이터를 보내거나 이메일/메시지를 실제로 발송하기 전에는 먼저 확인한다.
- 요구사항이 여러 해석이 가능할 정도로 애매하면, 임의로 정하지 말고 먼저 물어본다.

## 절대 안 되는 것
- `main`(또는 `master`) 브랜치에 직접 커밋하거나 강제 푸시(force push)하지 않는다.
- 비밀번호, API 키, 개인정보가 담긴 파일을 코드나 커밋에 포함하지 않는다.
- 사용자의 명시적 요청 없이 파일이나 폴더를 영구 삭제하지 않는다.
```

이 예시에는 특정 연구실, 특정 사람 이름, 특정 프로젝트 경로가 전혀 들어 있지 않습니다. 어떤 소프트웨어 프로젝트에도 그대로 복사해서 시작점으로 쓸 수 있습니다.

## 5. 실전 팁

- **짧게 시작하세요.** 처음부터 완벽한 규칙 파일을 만들 필요는 없습니다. 위 예시 정도로 시작해서, 실수가 생길 때마다 규칙을 하나씩 추가하는 방식이 훨씬 현실적입니다.
- **규칙은 구체적일수록 좋습니다.** "조심해서 작업해라" 같은 추상적인 말보다 "이 폴더는 건드리지 마라", "이 명령어는 쓰지 마라"처럼 구체적으로 적어야 AI가 실제로 따를 수 있습니다.
- **금지 규칙(③)은 최대한 명확하게.** 애매한 표현("웬만하면 하지 마라")보다는 단정적인 표현("절대 하지 마라")이 안전합니다.
- **주기적으로 다듬으세요.** 프로젝트가 커지면 규칙 파일도 길어집니다. 너무 길어지면 관련 주제별로 나눠서 별도 파일로 분리하고, 메인 파일에서는 그 파일들을 가리키기만 하는 것도 좋은 방법입니다.

## 6. 이 툴킷에서 시작하기

이 저장소(sci-toolkit) 최상위의 `AGENTS.md` 파일이 바로 이 문서에서 설명한 규칙 파일의 실제 자리입니다. 아직 비어 있다면:

1. 위 3단계 분류법(항상/물어볼 것/절대 안 됨)을 그대로 뼈대로 사용하세요.
2. 이 프로젝트에서 실제로 반복되는 상황(예: 어떤 폴더를 건드리면 안 되는지, 어떤 작업 전에 확인이 필요한지)을 하나씩 채워 넣으세요.
3. 개인정보·연구실 고유 정보·자격 증명은 넣지 마세요 — `.distignore`에 명시된 것처럼 이런 내용은 배포용 파일에 포함되면 안 됩니다.

`AGENTS.md`는 계속 자라나는 문서입니다. 완벽하게 쓰려고 하지 말고, 작게 시작해서 필요할 때마다 한 줄씩 추가하는 것이 가장 실용적인 방법입니다.
